## 1. What this is

This is the first working version of Realt AI, built from an empty repository against the product/engineering guide in `CLAUDE.md`. It is a real, running Next.js application — not a mockup — covering the full loop the guide describes:

> Understand user goals → detect conflicts → rank priorities → evaluate trade-offs → recommend → explain reasoning.

Concretely, a user can:

1. Land on `/`, read what Realt AI does, and start the flow.
2. Go to `/onboarding`, describe what they want in a home in their own words.
3. Have that free text turned into structured priorities (via an LLM call, or a deterministic fallback if no LLM is configured), then review and edit those priorities in a form.
4. Land on `/recommendations`, where every candidate property is scored against those priorities, ranked, and displayed with an explicit reason for its score — what fits, what's risky, what's a compromise — plus any conflicts detected between the priorities themselves (e.g. "critical short commute" + "critical tight budget").

Everything below documents exactly what was built, how it maps to the CLAUDE.md guide, what's real vs. placeholder, and what should happen next.

**Verification performed before calling this done:** `tsc --noEmit` (clean), `eslint .` (clean, zero warnings), `next build` (succeeds, all routes prerender), `vitest run` (24/24 tests pass), and a scripted Playwright run that actually drove a browser through the full flow (home → onboarding → describe → review → recommendations → theme toggle), screenshotting each step and checking for console/page errors. Only a single benign 404 was found (a stray favicon request before `app/icon.tsx` was added — since fixed).

## 2. Architecture

### 2.1 High-level shape

```
Browser
  │
  ├─ Server Components (pages, layout) ── rendered on the server, no client JS shipped
  │
  ├─ Client Components (onboarding flow, recommendations list, theme toggle)
  │     │
  │     └─ fetch() ──► Route Handlers (app/api/ai/*)
  │                         │
  │                         ├─ Zod validation (never trust client input)
  │                         ├─ In-memory rate limiter (per client IP)
  │                         │
  │                         ├─ services/ai/*        (priority extraction)
  │                         │     └─ OpenAI Responses API, or heuristic fallback
  │                         │
  │                         └─ services/matching/*  (scoring engine)
  │                               └─ lib/mock-properties.ts (stand-in for Supabase)
  │
  └─ sessionStorage ── hands priorities from /onboarding to /recommendations
                        (no backend persistence yet — see §5)
```

This is a standard Next.js App Router structure: Server Components by default, Client Components only where interactivity is required (forms, theme switching, fetch-driven UI), Route Handlers as the backend, no separate API server.

### 2.2 Why the design is split this way

**The scoring/explanation logic never touches the LLM.** This was a deliberate architectural choice, not an oversight. CLAUDE.md is explicit: *"Never hallucinate. Never fabricate facts. Never recommend something it cannot explain."* If a property's "why it fits" text were generated by an LLM describing the property, the model could describe an amenity or trade-off that isn't actually in the data — a hallucination risk baked into the core product experience. Instead:

- `services/matching/score-engine.ts` is a **pure, deterministic, fully-tested function**. It computes a score from real property/priority data and builds every sentence of the explanation from that same data. The number and the explanation cannot drift apart because they come from the same computation.
- The LLM is scoped to the one place natural-language understanding is actually needed and irreplaceable: turning a person's free-text paragraph into structured priorities (`services/ai/priority-extraction.ts`). Even there, it's constrained to a strict JSON schema (OpenAI Responses API `json_schema` / `strict: true` mode) so it cannot return arbitrary prose, and whatever comes back is **re-validated against the Zod schema before anything else in the app trusts it**.
- If no `OPENAI_API_KEY` is configured, or the API call fails for any reason, the app **does not break** — it falls back to `extractPrioritiesHeuristically()`, a small regex/keyword-based parser that only fills in fields it can actually find in the text and defaults everything else. The UI tells the user when this fallback is active ("Running in offline mode") rather than pretending it understood more than it did. This is what makes the whole app runnable and testable with zero external configuration or secrets.

**No database yet, by design.** Supabase is listed in CLAUDE.md as "planned," not present. Building a real persistence layer without a confirmed schema, auth model, and data-access pattern would mean guessing at all three and likely rebuilding them. Instead, `lib/mock-properties.ts` provides seed data typed identically to the future `Property` model, so swapping in Supabase later is a change to *one function* (how `app/api/ai/recommend/route.ts` fetches candidates), not a rewrite of the scoring engine or UI.

### `features/` — UI specific to one product area

This is where CLAUDE.md's "every feature owns its own components where appropriate" is applied literally.

**`features/onboarding/`**
- `priority-intake-flow.tsx` (Client Component) — the orchestrator. Two-step state machine: `"describe"` (free-text textarea → `POST /api/ai/priorities`) → `"review"` (editable form → save to session store → navigate to `/recommendations`). Shows a loading state during extraction, surfaces API errors inline, and displays an explicit "offline mode" notice when the heuristic fallback was used instead of the real model.
- `priority-review-form.tsx` — the editable form for everything in `UserPriorities`: budget min/max, commute minutes + mode (Radix `Select`), min bedrooms/bathrooms, must-haves/deal-breakers/lifestyle tags (via `TagListEditor`), and a 1–5 importance selector per category rendered as an accessible `radiogroup`.
- `tag-list-editor.tsx` — reusable add/remove tag input (Enter or comma to add, click-to-remove badges), used three times in the review form. Built once instead of copy-pasted, per CLAUDE.md's "never duplicate logic."

**`features/recommendations/`**
- `recommendations-list.tsx` (Client Component) — reads priorities from session storage on mount; if none exist, shows a "let's start with your priorities" empty state with a link back to onboarding instead of erroring. Otherwise calls `POST /api/ai/recommend`, handles loading/error states, and renders a conflict-warning card (if any) followed by the ranked list.
- `property-card.tsx` — one property's full result: price/beds/baths/sqft, the `MatchScoreBadge`, the plain-language summary, and three columns (why it fits / risks / compromises) built directly from the `MatchResult` the scoring engine produced. Deal-breaker-excluded properties render dimmed with the specific exclusion reason instead of a score.
- `match-score-badge.tsx` — a small, purely presentational score pill with three visually and semantically distinct tiers (strong/partial/weak match), using `role="img"` and a full-sentence `aria-label` so screen readers get the same information sighted users get from color.

### `services/` — orchestration and business logic, no UI

**`services/matching/score-engine.ts`** (308 lines — the largest and most important file in the codebase)

This *is* the Realt Thinking Framework as code:

- `detectPriorityConflicts(priorities)` — step 2. Currently checks three concrete conflict patterns: inverted budget range (min > max, high severity), short-commute + critical-commute + critical-budget (medium), and 4+ bedrooms + critical-space + critical-budget (medium). Returns `PriorityConflict[]` with human-readable descriptions.
- `scoreBudget`, `scoreCommute`, `scoreSpace`, `scoreSafety`, `scoreSchools`, `scoreLifestyle` — six independent, single-responsibility scoring functions, one per `PriorityCategory`. Each returns a `MatchFactor`: a 0–100 raw score, the user's importance weight for that category, a plain-language explanation string, and an `isRisk` flag.
- `scoreProperty(property, priorities)` — steps 3–6 for one property. Computes the weighted average across all six factors, detects deal-breaker matches (checked against amenities, description text, and lifestyle tags — case-insensitive), applies a penalty for each unmet must-have, and assembles `strengths` / `concerns` / `compromises` / a summary sentence, all derived from the factor data rather than freshly generated.
- `rankProperties(properties, priorities)` — maps `scoreProperty` over every candidate and sorts by score descending, with deal-breaker-excluded properties always pushed to the end regardless of their raw score.

**`services/ai/`**
- `client.ts` — thin wrapper around the OpenAI Responses API (`fetch` to `api.openai.com/v1/responses`) using `text.format.type: "json_schema"` with `strict: true` so the model's output shape is enforced server-side, not just hoped for. Exports `isAiConfigured()` and throws a typed `AiServiceUnavailableError` (not a generic error) when no key is present, so callers can distinguish "not configured" from "actually broke."
- `priority-extraction.ts` — `extractPriorities(freeText)` tries the AI path first (if configured), validates the result with `userPrioritiesSchema.parse()`, and falls back to `extractPrioritiesHeuristically(freeText)` on any failure. The heuristic function is intentionally conservative: it extracts a dollar figure via regex, bedroom/bathroom counts, a commute-minutes number, commute-mode keywords, a fixed list of lifestyle keywords, and bumps category importance to 5 only when the user explicitly used a relevant word ("school," "safe," "affordable"). It never invents a value it didn't find in the text — untested/unmentioned fields keep documented defaults. This function is directly unit-tested (see §6).

## 5. Production-ready vs. placeholder — an honest accounting

### Genuinely production-ready

- **The scoring engine** (`services/matching/score-engine.ts`). Pure functions, fully unit-tested, no hidden state, no I/O. This is real business logic, not a stub.
- **Input validation and API contracts.** Every route handler validates with Zod before doing anything; nothing client-supplied is trusted. This pattern doesn't need to change when real data sources are added.
- **The design system and theming.** Tokens, light/dark/system support, and the UI primitives are built the way they'd be built for a real product — no throwaway styling.
- **Accessibility fundamentals.** Semantic HTML, ARIA labeling (including on non-text elements like the match score badge and importance radiogroups), keyboard navigation, visible focus states, and a skip link are implemented and were manually verified, not assumed.
- **Security posture for what exists.** Server-only secrets (API key never touches the client), input validation at every boundary, and rate limiting on both AI-touching routes.
- **The AI integration pattern itself** — schema-constrained model output, server-side re-validation, graceful degradation — is the correct production pattern; it doesn't need to be rebuilt when scaled up.

### Explicitly placeholder — called out in `docs/architecture.md`, not hidden

- **Property data is static mock data** (`lib/mock-properties.ts`), six hand-written listings. There is no real inventory, no ingestion pipeline, no Supabase connection yet (Supabase is listed as "planned" in CLAUDE.md, not present in this build).
- **No persistence layer at all.** No accounts, no login, no saved searches. Priorities live only in `sessionStorage` for the current browser tab and vanish when it's closed. This is the single biggest gap relative to a real product.
- **Rate limiting is in-memory and per-process** (`lib/rate-limit.ts`). It works correctly for a single running instance but resets on redeploy and won't coordinate across multiple serverless instances — the file says so in its own comment. Needs a shared store (e.g. Upstash Redis) before horizontal scaling.
- **The heuristic priority-extraction fallback is intentionally simple** (regex/keyword-based). It's a safety net for when no AI key is configured, not a substitute for the real model — the UI tells the user when it's active rather than pretending otherwise.
- **No end-to-end or accessibility regression test suite.** The full flow was verified manually with a one-off Playwright script during this build (screenshots taken, zero console errors found), but that script isn't committed as a repeatable CI test yet.
- **No image assets for properties.** `Property.imageUrl` exists in the type for forward compatibility, but `property-card.tsx` currently renders a neutral icon placeholder rather than a photo, since there are no real photos to show yet.
- **No monitoring/observability, no CI pipeline, no deployment configuration** — this build has not been deployed anywhere; it has only been run and verified locally.

## 7. Next three highest-priority tasks

In priority order, before any new feature work:

### 1. Persistence layer (Supabase integration)

**Why this is #1:** every other placeholder in §5 traces back to this one. There's no way to save a user's priorities across sessions, support multiple users, store real property inventory, or make rate limiting reliable without a real database. This is also explicitly the next planned piece per CLAUDE.md's tech stack. Concretely: define the schema for `users`/`priorities`/`properties` (or reuse the existing `types/` shapes as the schema source of truth), replace `lib/mock-properties.ts` with a Supabase query behind the same interface, and replace `hooks/use-priorities-store.ts`'s `sessionStorage` calls with real reads/writes tied to a user or session ID. This unblocks accounts, saved searches, and revisiting past recommendations — all of which are core to "decision assistant," not "one-shot search."

### 2. Automated end-to-end and accessibility regression tests

**Why this is #2:** the golden path was verified by hand in this session, once. That verification has already expired — it doesn't run again on the next commit. Given CLAUDE.md's explicit testing priority on "critical user flows," the onboarding → review → recommendations path needs a committed Playwright (or equivalent) suite that runs in CI, plus an automated accessibility check (e.g. `axe-core` integration) so keyboard/ARIA/contrast regressions get caught before they ship, not discovered manually again next time.

### 3. Production-grade rate limiting and abuse protection

**Why this is #3:** the current rate limiter is correctness-tested logic sitting on a foundation (`Map` in process memory) that silently stops working the moment this app runs on more than one server instance — which is the default on most serverless platforms including Vercel. Since the AI routes are the most expensive and most abusable surface in the app (they call a paid external API), this should be fixed before real traffic, not after an incident. Concretely: swap `lib/rate-limit.ts`'s in-memory `Map` for a shared store (Upstash Redis is the natural fit alongside Vercel), and add basic abuse signals beyond raw request count (e.g. payload-size limits are already in place via Zod, but consider CAPTCHA or similar for the unauthenticated intake endpoint once it's public).
