# Architecture

This is the initial implementation of Realt AI: an onboarding flow that turns a
free-text description of what someone wants into structured priorities, and a
recommendations flow that scores candidate properties against those
priorities using the Realt Thinking Framework.

## Internationalization

Sweden is the initial market, so the app is localized (next-intl) with
Swedish as the default locale and English as the second. Routing uses
`localePrefix: "as-needed"`: Swedish serves at the bare path (`/`,
`/onboarding`), English at `/en`, `/en/onboarding`. Locale is negotiated
from the `Accept-Language` header (or a saved cookie) via `middleware.ts`,
and a `LocaleSwitcher` in the header lets a visitor override it explicitly.

- `i18n/routing.ts` — the single source of truth for supported locales.
  Adding a market is: add its code here, add `messages/<locale>.json`,
  nothing else changes.
- `i18n/navigation.ts` — locale-aware `Link`/`useRouter`/`usePathname`,
  used everywhere instead of `next/link` / `next/navigation` so internal
  links always resolve to the correct locale prefix.
- `i18n/request.ts` — server-side message loading per request.
- `messages/en.json`, `messages/sv.json` — every UI string in the app,
  namespaced by feature (`home`, `onboarding`, `recommendations`,
  `propertyCard`, etc.).
- `global.d.ts` — augments next-intl's types with our locale union and
  message shape, so `useTranslations`/`getTranslations` calls are
  type-checked against the actual message catalog (a typo'd or missing key
  is a build-time TypeScript error, not a runtime blank string).

**What is and isn't translated.** All UI chrome — navigation, buttons,
form labels, headings, empty/loading/error states, ARIA labels — is fully
localized in both languages. What is *not* yet localized: the *sentence
grammar* of the match explanations and conflict descriptions generated by
`services/matching/score-engine.ts` (see "Why explanations are
template-based, not LLM-generated" below) — those sentences are still
English regardless of UI locale. The *data* they report is correct
either way: mock listings are Swedish-market (SEK, m², real Swedish
cities — see `lib/mock-properties.ts`), and `lib/format.ts` formats prices
and areas with `sv-SE` regardless of UI language, the same way a real
listing site shows local currency/units no matter what language you're
browsing in. Translating the surrounding sentence templates themselves
(e.g. "Priced at X, within your Y–Z range.") into Swedish is
straightforward future work, tracked on the V1.0 roadmap; it just hadn't
been done yet as of this note.

## Folder structure

Feature-based, per `CLAUDE.md`:

- `app/` — routes, layouts, route handlers (App Router). Pages live under
  `app/[locale]/` (the dynamic locale segment); `app/api/`, `app/icon.tsx`,
  `app/sitemap.ts`, and `app/robots.ts` stay outside it since they're
  locale-independent (the sitemap lists both locale variants of each page).
- `middleware.ts` — locale detection and routing (next-intl), matched
  against every path except `/api`, `/_next`, and static files.
- `components/` — shared, feature-agnostic UI (`components/ui` holds
  shadcn-style primitives authored directly in the repo, not pulled from a
  registry, so tokens and behavior stay under our control).
- `features/` — UI that's specific to one product area (`onboarding`,
  `recommendations`), composed from `components/ui`.
- `services/` — orchestration and business logic with no UI: `services/ai`
  (OpenAI Responses API integration) and `services/matching` (the scoring
  engine).
- `lib/` — small stateless utilities (`cn`, validation schemas, rate
  limiting, mock data).
- `types/` — the domain model shared by services, API routes, and UI.
- `hooks/` — client-only state helpers.
- `tests/unit/` — business logic tests (see Testing below).

## The Realt Thinking Framework, concretely

The framework in `CLAUDE.md` maps to real code, not just prose:

1. **Understand user goals** — `services/ai/priority-extraction.ts` turns
   free text into a structured `UserPriorities` object, and the guided
   onboarding conversation (`features/onboarding`, see below) keeps asking
   short follow-up questions until it's actually confident it understands
   enough to proceed, not just once and done.
2. **Detect conflicts** — `detectPriorityConflicts` in
   `services/matching/conflict-detection.ts` flags when stated priorities
   compete with each other, and the recommendations page surfaces this
   before the results. See "Deep conflict detection" below — this is one of
   the two steps of the framework, but deliberately the most heavily
   invested-in, since it's the clearest expression of "understand people
   before properties" from `CLAUDE.md`.
3. **Rank priorities / 4. Evaluate trade-offs** — `scoreProperty` computes a
   per-category (`budget`, `commute`, `space`, `safety`, `schools`,
   `lifestyle`) score, weighted by the importance the user assigned each
   category.
4. **Recommend** — `rankProperties` sorts candidates by weighted score, with
   deal-breaker matches excluded regardless of score.
5. **Explain reasoning** — every `MatchResult` carries `strengths`,
   `concerns`, `compromises`, and a plain-language `summary`, all derived
   directly from the same data used to compute the score. Nothing in the
   explanation is generated separately from the number, so the score and its
   explanation can't drift apart. All of it is assembled into the Realt
   Decision Report (see below) — the actual page a user lands on, not a
   bare results list.

## Guided onboarding: a confidence-driven conversation

The onboarding flow (`features/onboarding/priority-intake-flow.tsx`) is a
small state machine — `describe → clarify* → review → editing` — built
around one idea: never ask a question the extraction step already
answered confidently, and never show the full form by default.

**Per-field confidence, not just a value.** `extractPriorities`
(`services/ai/priority-extraction.ts`) returns `{ priorities, source,
confidence }`. `confidence` (`types/onboarding.ts`) is a boolean per
essential field — `budget`, `commute`, `space`, `weights` — true only if
the person actually stated that information, false if it's resting on a
default. mustHaves/dealBreakers/lifestyleTags are deliberately excluded
from this set: an empty list is a legitimate answer for those, not a gap,
so asking about them unprompted would violate "never ask unnecessary
questions." Both extraction paths report this honestly:

- The heuristic parser sets a field's confidence flag exactly when its own
  regex/keyword match fired — it already knows whether it found something
  or fell back to `FALLBACK_DEFAULTS`, so this is a direct readout of
  existing logic, not new guessing. Its keyword vocabulary also recognizes
  common Swedish phrasing (`sovrum`, `badrum`, `skol-`, `säker`/`trygg`,
  `billig`) alongside English, since Swedish is the default locale and
  this heuristic path is what actually runs whenever `OPENAI_API_KEY`
  isn't configured — which is always, in this environment.
- The AI path is asked, in the same structured JSON-schema call that
  extracts priorities, to also self-report a `confidence` object — the
  system prompt is explicit that this must reflect whether the person
  actually said it, not whether the returned value looks plausible.

**Deciding what to ask, one question at a time.**
`services/onboarding/clarifying-flow.ts` is a small pure module —
`nextClarifyingField(confidence, askedFields)` returns the single
highest-priority field that's still unconfirmed, in a fixed order
(budget → commute → space → weights), or `null` once nothing is left to
ask. There's no cap beyond "the 4 fields that exist" — bounded, one at a
time, always skippable, which is what keeps a worst-case (a fully vague
description) from feeling like an interrogation rather than a genuinely
overwhelming number of questions.

**One purpose-built question, not the form.** `ClarifyingQuestion`
(`features/onboarding/clarifying-question.tsx`) renders exactly one
compact input for whichever field is being asked about — a budget range,
a commute mode + minutes, bedroom/bathroom counts, or a "pick up to two"
chip picker for what matters most — never the full multi-field form.
Every question has a "Not sure — skip this" action; skipping moves on
immediately rather than blocking, and the field's confidence stays false
so the final summary discloses it as an assumed default instead of
silently presenting a guess as understood.

**The structured profile, made legible.** Once nothing is left to ask
(confidence was high from the start, or every gap got answered or
skipped), the flow lands on `PrioritySummary`
(`features/onboarding/priority-summary.tsx`) — a compact, read-only
statement of budget, commute, space, and top priorities, plus any
must-haves/deal-breakers/lifestyle tags that were mentioned. This *is*
the "structured internal user profile" — it's the same `UserPriorities`
object `rankProperties` and `detectPriorityConflicts` already consume,
just made human-readable before the person commits to it, with an "Edit
details" escape hatch into the full form (`PriorityReviewForm`, unchanged)
for anyone who wants to see or correct every field directly.

## Deep conflict detection

`CLAUDE.md` calls out "detect conflicts" as its own step in the Realt
Thinking Framework, separate from scoring — and `services/matching/
conflict-detection.ts` treats it as a genuine product surface, not a
side effect of scoring. It runs *before* any property is scored, purely
against `UserPriorities`, and looks for two different kinds of problems:

- **Literal contradictions in the structured fields** — a minimum budget
  above the maximum, 4+ bedrooms demanded alongside a critical budget, a
  short commute demanded alongside a critical budget. These use the
  numeric fields (`budgetMin`/`budgetMax`, `commuteMaxMinutes`,
  `minBedrooms`, `weights`) directly.
- **Hidden trade-offs in free-text signals** — pets vs. rental
  restrictions, nature vs. city-center living, nightlife vs. noise
  sensitivity, working from home vs. a one-bedroom layout, accessibility
  needs vs. a preference for historic buildings, and others. There is no
  separate "do you have pets" field in the onboarding form; these are
  recognized as keyword signals inside `mustHaves`, `dealBreakers`, and
  `lifestyleTags` — the same open-vocabulary free-text arrays the AI
  extraction layer (and the manual review form) already write into. A new
  concept (say, "has a garden preference") is a new keyword set in
  `conflict-detection.ts`, not a schema migration or an onboarding
  redesign.

Each detected `PriorityConflict` carries `title`, `description` (why the
tension exists), `severity` (`low`/`medium`/`high`, an estimate of how
much it narrows the search or affects long-term satisfaction), and
`options: ConflictOption[]` — realistic compromises, each with its own
`longTermConsequence`. `CLAUDE.md` is explicit that Realt AI never
chooses for the user; this shape is the enforcement of that rule at the
type level; there's no field for "recommended option," only alternatives
presented side by side.

Because the heuristic (non-AI) priority extraction path is what actually
runs in this environment (no OpenAI key configured), `services/ai/
priority-extraction.ts` was extended alongside this feature to recognize
the same free-text signals — pets, "work from home", "wheelchair
accessible", "forever home", "might relocate", "growing family", and so
on — deterministically, from exact phrase matches only. It never infers a
signal that wasn't actually written, consistent with the rest of that
file's "never fabricate" discipline.

`services/matching/priority-helpers.ts` holds the two tiny functions
(`getImportance`, `clampScore`) shared between the scoring engine and the
conflict detector, so the two modules don't duplicate them or import from
each other.

## The Realt Decision Report

`/recommendations` is not a results list — it's the Realt Decision Report,
the single page CLAUDE.md calls "the heart of the product." Everything on
it is assembled server-side by `buildDecisionReport`
(`services/report/decision-report.ts`), a pure function of data already
produced elsewhere (`rankProperties`, `detectPriorityConflicts`). This
module adds no new scoring or conflict logic of its own — only
interpretation and framing — so the report can never claim something the
underlying data doesn't support.

**Two headline numbers, both explained, neither hidden behind jargon:**

- **Realt Score** — the best available match's score. If nothing clears
  the user's deal-breakers, it's honestly 0, not a misleadingly averaged
  number.
- **Confidence Score** — new for this feature: the percentage of the four
  essential fields (`budget`/`commute`/`space`/`weights`) the user actually
  confirmed, from the same `PriorityConfidence` the guided onboarding flow
  produces. This is why `hooks/use-priorities-store.ts` now persists
  confidence alongside priorities (defaulting to fully-confirmed for a
  saved search loaded from a past session, which never carried this signal
  to begin with — see the function's own comment for the reasoning). Low
  confidence deliberately doesn't use the same red/destructive tone as a
  weak property match — it means "tell us more," not "something's wrong."

**Sections that synthesize existing data, not new facts:**

- *Compromise analysis* is the top match's own `compromises` (missed
  must-haves).
- *Long-term consequences* is every conflict's own `ConflictOption.
  longTermConsequence`, most severe conflicts first, capped at 6.
- *Likely to appreciate* / *possible regrets after 12 months* are the top
  match's own strong (`score >= 75`) and risk (`isRisk`) factors, each
  paired with a category-aware framing sentence (`APPRECIATE_FRAMING` /
  `REGRET_FRAMING`) about why that *kind* of factor tends to matter more
  or less with time — the framing is generic per category, the fact is
  always specific to the property. These two lists and the underlying
  strengths/concerns lists are deliberately kept mutually exclusive (a
  factor scoring exactly 75 while also being a risk — e.g. missing a
  single bedroom — must never show up as both a reason to feel good and a
  reason to worry; see the `!factor.isRisk` guards in both
  `score-engine.ts` and `decision-report.ts`, and the regression tests
  covering it).
- *Important unanswered questions* combines unconfirmed fields (phrased as
  direct questions) with medium/high-severity conflicts (phrased as
  "which matters more to you?") — never low-severity ones, to avoid
  turning transparency into noise.
- *Suggested property matches* is `rankProperties`, filtered to
  non-excluded results and capped at `MAX_TOP_MATCHES` (5) — curated, not
  the full candidate list, on purpose.

**The property card is compact by default, not a wall of text.** Image,
title, street + house number (`lib/address.ts` splits `Property.address`),
municipality, price, Realt Score, and a one-line reason are always
visible; the full critical-concern callout, strengths/risks/compromises
grid, and per-factor breakdown are one click away behind a `<details>`
disclosure, same accessible pattern as `MatchBreakdown`. A "View original
listing" badge sits exactly where a real Hemnet/Booli/broker/landlord
link will go later — deliberately a plain, honest `<span>`, not a dead
link or a disabled `<button>` nested inside a `<summary>` (which would be
invalid HTML), since no real listing exists yet.

**Built to be saved, not just read once.** The header's "Print / Save as
PDF" button is a plain `window.print()` call; `site-header.tsx` and
`site-footer.tsx` carry `print:hidden` so a printed/PDF'd report is just
the report, not the site chrome around it. No new infrastructure — native
browser print is enough to make the report something a person can keep.

## Why explanations are template-based, not LLM-generated

`CLAUDE.md` says the AI must never hallucinate and must always be able to
explain a recommendation. Free-form LLM text about *why* a specific property
fits is a hallucination risk — the model could describe an amenity or
trade-off that isn't actually in the data. The scoring engine instead builds
explanations deterministically from the same property/priority data it
scores against, which is both fully explainable and trivially testable.

The LLM's role is scoped to the one place natural-language understanding is
actually needed: turning a person's free-text description into structured
priorities (`services/ai/priority-extraction.ts`). Even there:

- The model is constrained to a strict JSON schema (OpenAI Responses API
  `json_schema` mode), so it can't return arbitrary text.
- Whatever comes back is re-validated against the Zod schema
  (`lib/validation.ts`) before it's trusted anywhere else in the app.
- If no `OPENAI_API_KEY` is configured, or the request fails, extraction
  falls back to `extractPrioritiesHeuristically` — a small deterministic
  parser that only fills in fields it can find in the text, defaulting
  everything else instead of guessing. The app is fully usable with zero
  external configuration; the UI tells the user when it's in this "offline
  mode" via `PriorityIntakeFlow`'s review step.

## Data layer, accounts, and saved searches

`services/persistence/` defines the data layer as three repository
interfaces — `AccountRepository`, `SavedSearchRepository`,
`PropertyRepository` — selected by `getAccountRepository()` /
`getSavedSearchRepository()` / `getPropertyRepository()`. Every caller goes
through the interface, never a concrete implementation directly.

**Accounts and saved searches now have two implementations each:**
in-memory mocks (`services/persistence/mock/`) and real Supabase-backed
ones (`services/persistence/supabase/`, `SupabaseAccountRepository` /
`SupabaseSavedSearchRepository`, using `@supabase/supabase-js` with the
server-only secret key). The factory in `services/persistence/index.ts`
picks Supabase automatically the moment `SUPABASE_URL` and
`SUPABASE_SECRET_KEY` are both set, and falls back to the mocks otherwise
— no code changes either way. See `docs/supabase-setup.md` for the
one-time migration (`supabase/migrations/0001_init.sql`) and environment
variables needed to turn this on.

**`PropertyRepository` deliberately stays mock regardless of Supabase
configuration.** There's no real Swedish listings source connected yet
(roadmap item #8), and building a Supabase properties table now would mean
guessing at a schema for data that doesn't exist — likely wrong once a
real vendor is chosen. This is the one place the factory doesn't follow
the "switch automatically" rule, on purpose.

**Mock authentication** (`app/api/auth/*`, `lib/session.ts`,
`components/account-provider.tsx`) is a separate axis from persistence and
is *not* wired to Supabase yet — entering an email still signs someone in
immediately, no password, no email actually sent, the account created on
first use via `AccountRepository.findOrCreateByEmail` (which now may write
to real Supabase, but nothing verifies the email belongs to the person
typing it). This is deliberately the same UX shape a real passwordless
flow (e.g. Supabase Auth's email OTP/magic link) would have, so replacing
it later changes what happens on the server while someone waits, not how
they sign in. The session itself is a signed cookie (HMAC-SHA256 via
`SESSION_SECRET`, see `.env.example`) — not full session management (no
rotation, no revocation), but enough that a client can't simply set
`realt_session=<any-account-id>` and impersonate another account.

**Saved searches** are the product feature this unblocked:
`SaveSearchButton` on `/recommendations` persists the current priorities
via `POST /api/saved-searches` for a signed-in account; `/my-searches`
lists them and lets someone revisit a past search (which replays through
the existing `sessionStorage` handoff into `/recommendations` — no new
mechanism needed there) or delete it.

Two things worth being precise about:

1. **Without Supabase configured, this is mock persistence — process
   memory, not durable.** Data does not survive a restart and does not
   coordinate across multiple instances. With Supabase configured, this
   limitation goes away for accounts and saved searches specifically
   (property data is still mock either way, see above).
2. **Priorities still also flow through `sessionStorage`**
   (`hooks/use-priorities-store.ts`) for the onboarding → recommendations
   handoff regardless of sign-in state — saved searches are additive, not
   a replacement for that mechanism.
3. **The Supabase implementations were written without live verification**
   — the environment they were built in blocks outbound access to
   `supabase.co` at the network-policy level. They're covered by unit
   tests against a mocked Supabase client
   (`tests/unit/supabase-persistence.test.ts`), which verifies the
   repositories' own logic (mapping, error handling, the unique-violation
   race-condition fallback on account creation, ownership-checked
   deletes) but cannot prove the live connection works. See
   `docs/supabase-setup.md` for how to close that gap.

## Security

- All API route input is validated with Zod (`lib/validation.ts`) before
  touching any business logic — the client is never trusted.
- `services/ai/client.ts` only reads the API key from `process.env`, never
  from a request; nothing client-supplied can change which credentials are
  used or where a request goes.
- `lib/rate-limit/` rate-limits both AI-touching route handlers by client
  IP, via a pluggable `RateLimiter` interface (see below) rather than one
  hardcoded implementation.

## Rate limiting

`lib/rate-limit/` defines a small `RateLimiter` interface with two
implementations, selected automatically by `getRateLimiter()`:

- `InMemoryRateLimiter` — a fixed-window counter in a `Map`. Correct for a
  single running instance; used whenever no shared store is configured.
  This is what runs today, since nothing is deployed yet.
- `UpstashRateLimiter` — the same fixed-window algorithm against Upstash
  Redis's REST API (a pipelined `INCR` + `PEXPIRE ... NX`, so the window's
  expiry is set atomically on the first request rather than racing a
  second round trip). Activates automatically the moment
  `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` are set — no code
  changes required, matching the same "the app upgrades itself once real
  infrastructure exists" philosophy as `services/ai/client.ts`.

`checkRateLimit()`, the function the route handlers actually call, wraps
whichever limiter is active and **fails open** (allows the request) if it
throws — a rate-limiter outage should degrade availability, not take down
the routes it exists to protect. This is deliberately different from the
AI extraction path, which fails closed into the heuristic fallback: being
wrong about a rate limit for a few seconds during an outage is a much
smaller risk than an AI route going fully unprotected being treated the
same as it going fully down.

## Known limitations (by design, for this stage)

- **Accounts, sessions, and saved searches are mocked, not durable.**
  Everything lives in server-process memory (see "Data layer, accounts, and
  saved searches" above) and is lost on restart. Real accounts and durable
  storage are what Supabase integration replaces this with.
- **Property data is static mock data**, not a real inventory.
- **CI is authored but not active.** `.github/workflows/ci.yml` runs
  typecheck/lint/tests/build and the full E2E suite on every push and PR —
  but it can't actually run until GitHub push access is restored to this
  repository.
- **Legal pages are drafts, not reviewed by counsel.** `/privacy` and
  `/terms` accurately describe what the app does today, but carry a visible
  draft notice and placeholder business-identity fields; they are not a
  substitute for real legal review before a public launch.

## Testing

Per `CLAUDE.md`, tests prioritize business logic over UI, but "critical
user flows" and accessibility are explicit requirements too, so both are
covered by two separate, purpose-built suites rather than one.

**`tests/unit/`** (Vitest) — business logic, no browser involved:

- The scoring engine's budget/commute/space/safety/schools/lifestyle
  scoring, deal-breaker exclusion, and must-have compromise detection
  (`score-engine.test.ts`).
- The deep conflict-detection engine — all 14 rules, plus a structural
  test that every conflict returned always has a title, description,
  severity, and at least one option with a consequence
  (`conflict-detection.test.ts`).
- Input validation edge cases (`validation.test.ts`).
- The deterministic priority-extraction fallback, including its per-field
  `confidence` reporting and Swedish keyword coverage
  (`priority-extraction.test.ts`).
- The guided onboarding decision engine — `nextClarifyingField` ordering,
  the skip-still-counts-as-asked rule, and the hard cap at 4 questions
  (`clarifying-flow.test.ts`).
- The Realt Decision Report builder — confidence-score math, priority
  ranking order and tie-breaks, compromise/long-term-consequence/
  appreciate/regret derivation, the mutual-exclusivity guarantee between
  appreciate and regret, open-question generation, and the top-matches cap
  and exclusion filtering (`decision-report.test.ts`).
- The street/house-number address parser (`address.test.ts`).

Run with `npm run test`.

**`tests/e2e/`** (Playwright, against a production build — not `next dev`,
since dev-mode's on-demand compilation and slower hydration produce
flakiness that has nothing to do with the app) — real user flows in a real
browser:

- `golden-path.spec.ts` — the full home → onboarding → summary →
  recommendations flow, once in Swedish and once in English, with a
  fully-specified free-text answer that asserts the guided onboarding
  flow correctly skips every clarifying question when it's already
  confident, rather than asking anyway.
- `guided-onboarding.spec.ts` — the clarifying-question loop itself: a
  vague description asks budget, then commute, then space, then "what
  matters most," in that order, one at a time; skipping a question moves
  on and the summary discloses it as an assumed default; "Edit details"
  from the summary opens the full form and "Back" returns to the summary
  without losing progress.
- `locale-switcher.spec.ts` — switching locale via the header control, and
  that it preserves the current page rather than bouncing to the homepage.
- `empty-recommendations.spec.ts` — visiting `/recommendations` with no
  prior priorities shows the guided empty state, not an error.
- `theme-toggle.spec.ts` — the light → dark → system cycle updates both the
  control's accessible name and the document's `dark` class.
- `accessibility.spec.ts` — `@axe-core/playwright` scans of the home,
  onboarding, and recommendations pages (both locales) against WCAG 2.0/2.1
  A and AA, asserting zero violations — including the new guided-onboarding
  clarifying-question and summary screens specifically, not just the
  describe step. This is what caught a real bug during
  development: the "partial match" score badge's amber text failed contrast
  (3.17:1 against its own tinted background, needed 4.5:1) — fixed by
  darkening the `--warning`/`--success`/`--destructive` design tokens in
  `globals.css` (verified by direct WCAG relative-luminance calculation
  against each token's actual `/10`-opacity badge background, in both
  themes, not just spot-checked).

Run with `npm run test:e2e`.
